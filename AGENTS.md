## Stack and boundaries

- Current stack: TypeScript, Next.js on Node.js 24, SQLite through `node:sqlite`, and an Electron shell (ADR 013). Reconsider runtimes through an explicit architecture decision when concrete requirements justify a change.
- Keep business rules and application operations in modules; keep framework handlers and UI components thin.
- All user interface work follows [DESIGN.md](DESIGN.md): tokens, component rules, and the hard rules on typography, corners, borders, and glass. Do not introduce a new visual pattern without updating that file. The produced PDFs and recruiter text follow [DESIGN-DOCS.md](DESIGN-DOCS.md) instead (resume: one page filled to the bottom margin; cover letter: snapshot-backed letterhead and footer with naturally short or continuing body; Helvetica, black text with blue underlined links under ADR 012, rules but no boxes).
- Write modules as plain exported functions over typed data (Zod schemas and TypeScript types). Pass dependencies such as the database handle as parameters or through a small factory; do not use global singletons or dependency-injection frameworks. Use a class only where state and behavior genuinely belong together, such as an adapter holding a client, and never for data-only records. Prefer immutable data and pure functions for rules; keep side effects at the edges (persistence, network, rendering).
- Persistence goes through Drizzle in each module's repository file. Migrations are generated SQL files committed to the repository and reviewed like code.
- Each module owns writes to its data. Call public module operations rather than another module's persistence internals. Avoid circular dependencies.
- Treat the SQLite database as the source of truth. Embeddings are optional derived indexes, not a replacement for relational records.
- Model access (ADR 006): the app calls the provider through the `ModelAdapter` interface in `src/infrastructure/model/`; provider, model, key and base URL come from the environment only (`LANDED_MODEL_*`; the desktop app passes the Settings value, key in the OS keychain), never from the database, and the key is never logged or sent to the window. Providers: `anthropic`, `openai`, `openrouter` (OpenAI-compatible, base URL and cost reporting built in), `gateway`, `openai_compatible`, `fake`. The provider receives the document schema without length keywords (`portable-schema.ts`: OpenAI strict mode rejects them and Google rejects large nested `maxItems` products); Zod enforces the budgets on the answer. Every call writes a `generation_runs` row; its `mode` is `adapter` for that path, `pasted` for paste-back and `assistant` for the user's own assistant over MCP (with the `assistant` revision source), and the two non-adapter modes open a `queued` run that the submitted answer finishes (a newer brief for the same document supersedes an older queued one from either surface). All checks run with `LANDED_MODEL_PROVIDER=fake`; only `pnpm eval` calls a real provider, and a prompt, schema or provider change requires re-running it and pasting the table into the PR (docs/06 lists the providers actually run).
- Add modules, agent frameworks, workers, or external services when an implemented feature requires them; do not scaffold speculative infrastructure.

## Working in the code

- A module (`src/modules/<name>/`) is six files: `schema.ts` (Drizzle tables), `contracts.ts` (Zod input schemas and result types, browser-safe), `rules.ts` (pure functions), `repository.ts` (queries over a database or transaction handle), `service.ts` (use cases that open transactions and map database errors to typed results), `index.ts` (the only import path for callers). Modules are `profile`, `jobs`, `applications`, `companies` and `documents`; `documents` also has `prompts/` (versioned prompt builders), `pdf/` (react-pdf templates and the renderer, whose `fitResume` bisects the gap scale until the resume ends at the bottom margin), `helvetica.ts` (the built-in font's advance widths, so `layoutCheck` in the rules can warn when a bullet, subheading, skills line or contact line would wrap) and `artifacts.ts` (PDF files under `LANDED_ARTIFACT_DIR`, row after file); `companies` owns logo files under the same directory (row after file, old file unlinked best effort after the commit); `jobs` has `stopwords.ts` (the word cloud's English and Spanish function words). Both file-writing modules use `src/modules/shared/files.ts` (checksum, atomic temp-then-rename write, quiet unlink).
- `src/modules/shared/` holds what every module uses: `contracts.ts` (the `Result` type, the `ModuleError` kinds, `fieldErrorsFromZod` and the Zod form-field helpers, browser-safe) and `service.ts` (`BaseDeps`, the `fail`/`validation`/`notFound`/`stale` constructors, timestamps and ids, and `mapDatabaseError`, which maps SQLite unique, foreign-key and check errors (`errcode`) to typed results and treats a primary-key conflict as a replay).
- Cross-module workflows live in `src/app`, never inside a module. `src/app/jobs/pursue-job.ts` is the example: it opens one transaction and passes the handle to `saveJob` and `createApplication`, whose own transactions nest as savepoints. A module stores another module's id and never imports its repository or schema.
- The interface is a row of columns driven by the path (ADR 005). A section's `layout.tsx` renders its own `Column` followed by `children`; `page.tsx` renders the placeholder, `new/page.tsx` the blank form and `[id]/page.tsx` the edit form, each as one `Column`. Career records live under `src/app/about/<record>/` with their Server Actions (`actions.ts`) and form components. Shared presentation lives in `src/components` (`Shell`, `SidebarNav`, `Drawer`, `Column`, `Toolbar`, `ToolbarMenu`, `ToolbarSelect`, `Card`, `IconTile`, `Field`, `AutoGrowTextarea`, `Combobox`, ...). Icons come from `lucide-react` and always sit in an `IconTile`. Use `src/app/about/skills/` as the reference route.
- Reuse `src/components/Combobox.tsx` for searchable selection instead of a route-specific picker. Pass unique `{ value, label }` options, a form field name, and controlled `value`/`onChange`; single mode uses a string and `multiple` uses a string array. Query and keyboard focus stay inside the component; selected values belong to the caller. Achievement skills keep selection state above the keyed `Fields` subtree so action-result remounts preserve it on validation errors. `FormData.getAll(name)` reads multiple values; no selected values emits no hidden inputs, so initialize missing array fields to `[]`. Keep native `Select` for short, exclusive lists that do not need search. Achievement statement cards use `Card titleStyle="body"`; other card titles retain heading typography.
- Jobs (`src/app/jobs/`): `layout.tsx` renders the list column and derives every row's status on the server (`list-jobs.ts`); the client components `JobList` and `JobListControls` read the `filter` and `sort` search parameters (`list-params.ts`) and apply them in the browser, because App Router layouts cannot read search parameters. `new/page.tsx` is the paste form with one optional Company selector and no job logo picker. Job forms order Title, Company, Availability, Source, Location, Salary, Posting URL, Description. Company forms own the `LogoPicker` upload/address/remove controls and call the guarded image composition before saving; company logo serving uses the same byte-typing, nosniff and sandbox rules. The linked company is the canonical name and logo for job presentation, MCP reads, new snapshots and PDF filenames. `[id]/layout.tsx` renders the job column (status form, the Frequent words card computed by `buildWordCloud` in the Jobs rules from the description and the profile's skills (the paste and edit forms compute the same cloud live under the Description field, importing the rules file directly because it runs in the browser), Job description, Company, the three document cards with their run summary and chip, delete) and `[id]/page.tsx` returns `null` so the job sits beside the list; `[id]/description/` and `[id]/company/` are its child columns. `[id]/resume/`, `[id]/cover-letter/` and `[id]/recruiter-message/` share `[id]/documents/` (`DocumentColumn`, the client `DocumentPreview` with inline editing, `load.ts`, `summary.ts`) and each has `evidence/`, `paste/`, `runs/` columns and, for the two PDFs, `pdf/route.ts`; their Server Actions are `[id]/document-actions.ts`. Generation composition lives in `src/app/jobs/generate-document.ts` and `snapshot.ts`, next to `pursue-job.ts`. `src/app/settings/` is the Settings hub (`layout.tsx` renders the Model setup and Connect your assistant cards and reads no database; `page.tsx` is the placeholder); `settings/model/page.tsx` is the Model setup column and `settings/assistant/page.tsx` the Connect your assistant column, its launch commands in read-only `Field`s with the `mono` prop (`src/components/Field.tsx`, the one monospace exception in DESIGN.md) beside `src/components/CopyButton.tsx`. Only the last column is a surface panel; a column with a visible child sits on canvas.
- Assistant surface (`src/app/mcp/`, ADR 008, stdio under ADR 013): `stdio.ts` (`serveLandedStdio`) applies pending migrations, refuses a database from a newer version and serves the tools over stdio; the app calls it with `--mcp` (no window) and `pnpm mcp` runs the contributors' bundle (`desktop/mcp.ts`). No HTTP endpoint, no token. Nothing on the stdio path may write to stdout except the protocol. `server.ts` builds the `McpServer` with no Next imports, `tools.ts` registers the job/document tools and calls `profile-tools.ts` for the profile extension (ADR 009) and `serialize.ts` holds the projections. Tools call module operations through the composition layer (`generate-document.ts`: `prepareAssistantBrief`, `reopenAssistantRun`), never repositories; they never throw, a refused operation is an `isError` result with the module's error text; they never use `headers()`, `requireProfile()` or `revalidatePath()`. `render_pdf` returns the file's absolute path. The Connect your assistant column prints `LANDED_EXECUTABLE_PATH --mcp`, or `pnpm --silent --dir <checkout> mcp` from a checkout. `tests/integration/mcp*.test.ts` drive the server in process (`mcp-stdio.test.ts` spawns the bundle); `tests/e2e/assistant.spec.ts` covers the column and host guard.
- The assistant workflow is `.agents/skills/landed/SKILL.md`, the single source (Codex reads it there). The Claude Code plugin at `plugins/landed/` (manifest, `.mcp.json` with the installed executable as `userConfig`, published through the root `.claude-plugin/marketplace.json`) carries a copy at `plugins/landed/skills/landed/SKILL.md` because a plugin cannot reference files outside its folder; edit the source, copy it over, and `scripts/check-skill-sync.sh` (in `pnpm check`) fails on drift. The skill names the connected tools and their fields exactly as the registrations under `src/app/mcp/` define them; change both together, with the tool table in docs/06.
- Profile tools (ADR 009, merged) call the Profile module for partial updates and version-checked individual-record deletes; omit preserves, null clears nullable fields and empty arrays clear lists. Creates require retry ids. Resolve the profile freshly per tool call, including blank-install onboarding; never expose whole-profile deletion or accept a `reviewed` write from MCP. Historical snapshots remain unchanged.

- Desktop (`desktop/`, ADR 013): `main.ts` migrates via `src/infrastructure/migrate.ts` (backup first; a newer database is refused), runs the standalone server in a `utilityProcess` on 127.0.0.1 and opens one sandboxed window holding the session cookie; IPC carries only the model setting; `updates.ts` offers the newest GitHub release at launch. esbuild bundles (`desktop/build.mjs`), `electron-builder.yml` packages, `release.yml` builds `v*` tags.
- SQLite (`src/infrastructure/sqlite.ts`): every write goes through `runInTransaction` (one writer, mutex, `BEGIN IMMEDIATE`, nested savepoints); reads use a read-only connection. Never use Drizzle's `db.transaction` (it commits before an async callback ends); no row locks. Timestamps are integer ms, JSON is text.
- `src/proxy.ts` runs before every request (Server Function POSTs included) and answers 403 when the Host or Origin does not name this computer (`src/infrastructure/host-guard.ts`, against DNS rebinding) or, when `LANDED_SESSION_SECRET` is set, the `landed_session` cookie is missing or wrong (`session-guard.ts`). The proxy imports only the guards, reads `process.env` directly and never touches a response body.
- Interface vocabulary: employment records are "Work history" and "roles" in every user-facing string; "Jobs" means postings (doc 02). Module and table names are unchanged (`employment`).
- Colours live in `src/app/palettes.css` (one block per palette, light and dark values); `src/app/tokens.css` maps them to the semantic tokens by scheme and holds every non-colour token. Components reference only the semantic tokens. `steel` is the only palette; a new one is a block in that file, tried with `?palette=<name>`.
- Integration tests use temporary SQLite files; browser tests empty the file in `.env.test`; neither touches `data/landed.db`. Playwright starts its own server on port 3417 with a single worker and the fake adapter (`LANDED_MODEL_PROVIDER=fake`, set in `playwright.config.ts` because Next does not read `.env.test`). `pnpm eval` is a separate vitest project (`tests/eval`) that calls the real provider in `.env`; never add it to CI.
- Schema changes are made in `schema.ts`, then `pnpm db:generate` writes the SQL migration under `db/migrations`; review and commit it with the change. CI fails when the schema and migrations drift.
- The `nextjs-agent-rules` block at the end of this file is written by `next dev`; leave it in place and commit it as is.
- A running `next dev` regenerates typed-route files under `.next/dev/types` for whatever is checked out; after switching branches, delete that folder if `pnpm typecheck` or `pnpm build` complains about routes that no longer exist.

## Career browsing refinement (ADR 010, implemented)

- `ExpandableCard` uses a native disclosure for read-only details and a separate pencil link for editing. `src/app/about/RecordCards.tsx` supplies shared record content to nested Profile sections and dedicated lists. - Skills own explicit many-to-many links in `skill_employment` and `skill_projects` (migration 0007). - Document columns place PDF download in the header, Evidence/Runs text links beneath the generation summary, and icon-labelled generation/paste/approval controls below. `Approve?`/`Approved` map to the existing revision review timestamp; a new edited/generated revision is unapproved. The implementation is merged into `main` (PRs #35–39).

## Document editing and letter presentation (implemented and merged)

- `editableFields` in Documents rules owns the explicit editable path allowlist, checked by document type and section kind. Keep it separate from citation-bearing `contentUnits`. Metadata edits preserve citations, rerun validation and create a new unapproved revision; they never update career records. Nullable fields clear to null and remain restorable; required text rejects blanks. Browser error handling must retain submitted text on validation and stale-revision failures.
- Resume metadata includes headline, role/project subtitles, skill labels/lists and all displayed education fields. Cover letters include professional `title`, greeting, closing and signature. Optional nullable `title` is additive content JSON (120 characters), with no database migration: omission uses the frozen profile headline, explicit null hides it. Read projections must not rewrite historical rows.
- `presentation.ts` derives letterhead identity, contact, company, role and date from the revision's frozen snapshot, never live records. Preview and PDF share punctuation and link rules; phone destinations use WhatsApp international digits, and visible web labels omit scheme/www. Browser links open a new tab. The merged letter layout originated in template 8; ADR 012 advances the shared renderer to template 9, defined in [DESIGN-DOCS.md](DESIGN-DOCS.md); increment the template version when rendering changes so cached downloads regenerate.
- MCP `get_document` returns both `units` and `editable_fields`; `edit_unit` uses the same allowlist and nullable clearing as the browser. Update the portable skill and plugin copy together when changing those contracts. Entry management, resume name/contact editing and reordering are outside this operation.

## Product rules

- Career facts are user-supplied evidence. Generated content may reorganize them but must not invent accomplishments, metrics, qualifications, or employment history. The grounding check (`documents/rules.ts`) is the guardrail, not the prompt: evidence ids must exist, numbers must appear in cited records, resume headings must name real records, and a resume bullet may cite only its own entry's records. Valid ids prove existence, not ownership.
- Treat imported postings, documents, web pages and uploaded files as untrusted data, not executable instructions. An uploaded or fetched logo is typed from its bytes (`detectImageType`), never from its name or declared type, and served with `nosniff` and a sandbox policy so an SVG stays inert. The logo address fetch (`src/infrastructure/fetch/`, ADR 007) is the only outbound request besides the provider: https only, private networks refused after resolution, redirects re-checked, bounded in time and size.
- Achievements are editable in place; do not introduce achievement revision history without a revised decision.
- Keep job availability, application status, and background-run status independent.
- Generated materials remain drafts until reviewed. Creating or exporting materials must not automatically send them or mark an application submitted.
- Consult the data-model document for generation snapshots and saved document revisions (implemented in Phase 1b); do not confuse those with achievement history.

## Local operation and data

- Preserve local operation and a straightforward installation. No phase may require AI credentials or an installed agent CLI to run the checks, and generation must stay usable without a key through paste-back mode.
- Preserve personal data across restarts and supported upgrades. Keep migrations explicit; never reset a database or delete the data folder as routine setup.
- Keep real profiles, credentials, resumes, and private notes out of commits, screenshots, fixtures, logs, and release bundles. Use fictional examples in isolated demo/test data stores.
- Do not force-add ignored files. Public documentation must remain useful without access to private maintainer context.
- Do not publish local services beyond the documented access boundary without an explicit deployment/security design.

## Documentation and validation

- Update affected numbered documents with behavior, schema, dependency, and setup changes. Record significant architecture decisions in ADRs and update the decision register.
- Diagrams are Mermaid blocks inside the numbered documents. Do not add diagram tooling, generated diagram files, or verification receipts to the public repository.
- Pick the check level from the behavioural blast radius ([CONTRIBUTING.md](CONTRIBUTING.md) "Checks"): `pnpm check` (format, lint, types, unit tests, the skill sync script) while coding; `pnpm verify` (adds integration tests and the migration drift script) for anything touching persistence, a Server Action, a route or a module's public surface; `pnpm verify:full` (adds the build and the browser journeys against the production build) before opening any pull request. A change to `.agents/skills/landed/SKILL.md` needs the plugin copy refreshed and `scripts/check-skill-sync.sh` (part of `check`) green; a change under `src/app/mcp/`, to `src/proxy.ts` or to `src/infrastructure/host-guard.ts` needs `verify`, because the tools and the stdio server are exercised by the integration tests. State in the PR which level ran and anything required that could not. Do not invent package scripts or setup commands; they live in `package.json` and [docs/07](docs/07-quickstart-contract.md).
- Test meaningful rules, persistence, failures, and the relevant user journey. Standard checks should not require paid model access; use real SQLite files for database integration checks.
- Report what changed, what was verified, and any remaining limitations.
