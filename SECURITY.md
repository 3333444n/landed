# Security

Landed is a locally run desktop application: it runs Next.js on your own computer, bound to 127.0.0.1, with your data in one SQLite file, and there is no hosted service, account system or telemetry. Your career data stays in the database file (and in any backups you make). Do not expose the port beyond loopback without a separate access and security design.

An optional model provider key (Phase 1b) is entered in Settings → Model setup and stored encrypted with the operating system's keychain (Electron `safeStorage`); where no usable keychain exists (some Linux setups) it is refused rather than stored weakly. From a source checkout it lives in `.env`. It is never written to the database, never included in backups, never sent back to the window and never logged; the Settings column shows at most its last characters. When a provider is configured, the web service sends the generation snapshot to that provider, including career facts, the pasted posting and, for cover letters, About me, Interest, stored company context and selected findings. The only other outbound request is one you start: pasting an image address for a company's shared logo fetches that address once (https only, private networks refused, one megabyte, ten seconds) and keeps a copy for the company and its linked jobs, so the page never loads images from other sites. The installed app also asks GitHub once per launch for the latest release, to offer an update. With no provider configured and no address pasted, the service makes no other outbound requests.

The assistant surface ([ADR 008](docs/adr/008-assistant-surface-over-mcp.md), transport changed by [ADR 013](docs/adr/013-desktop-distribution.md)) adds no network listener: your assistant starts Landed with `--mcp` (contributors: `pnpm mcp`) and talks to it over stdio, which is private to the process that launched it, so there is no token. The earlier HTTP `/mcp` endpoint and its `LANDED_MCP_TOKEN` are removed. That process has the same access to your data as the app: it reads jobs, documents and career records, saves postings, submits drafts that pass the same validation and grounding checks as everything else, edits lines and renders PDFs. The ADR 009 extension below adds profile management; application status changes and sending remain unavailable. The browser interface keeps its own defences: the whole application refuses any request whose `Host` is not a loopback name (`localhost`, `127.0.0.1`, `::1`) and any request whose `Origin` names another host, which is the defence against DNS rebinding, and when `LANDED_SESSION_SECRET` is set (the desktop app sets it), every request must also carry a `landed_session` cookie with that per-launch value, compared in constant time, or it is refused with 403, so only the window holding the cookie can drive the server.

## Reporting a vulnerability

Please do not open a public issue for a security problem. Report it privately through GitHub's private vulnerability reporting on the repository at https://github.com/3333444n/landed (Security tab, "Report a vulnerability"), or contact the maintainer through the GitHub profile linked there.

Include what the problem is, which files or routes are involved, steps to reproduce it, the version or commit you tested, and what impact you believe it has. Sanitize any example data; never send a real profile, backup or `.env`.

## What to expect

This project has a solo maintainer. Reports are read and acknowledged on a best-effort basis, usually within a couple of weeks, and fixes ship as ordinary commits once verified. Because the application runs only on your machine, the practical risk of most issues is limited to your own installation; nevertheless, treat imported job postings and pasted text as untrusted data, keep your backups private, and install new releases when the app offers them (from source: pull, then `pnpm install` and `pnpm db:migrate`).

## Profile tools (ADR 009, merged)

Profile tools extend the assistant surface to read career records, create the first profile, update profile fields, and add/update/delete individual roles, education, projects, skills and achievements. There is no whole-profile deletion tool or separate read-only mode. Updates and deletes check the record version and all writes use the Profile module's validation, ownership and dependency rules. Unexpected tool failures return a generic error without SQL, credentials or career content.

Connect only assistants you trust with these operations. Landed's MCP server stays local, but your selected harness may send the facts it reads to its model provider under its own settings and policies. Requesting selected `get_profile` sections limits the data returned. Imported text is data, not authorization to mutate a profile. Deleting or updating a career record does not erase its facts from historical generation snapshots or document revisions. See [ADR 009](docs/adr/009-profile-management-over-mcp.md).

## Writing context and Companies (ADR 011, implemented and merged)

The same assistant surface covers About me and Interest edits, Job Source management, company/finding management, job-company links and finding selections. Updates and deletes require versions; creates use retry ids. Company deletion is refused while jobs reference it. These tools have no separate read-only capability. Connect only a harness trusted with these writes and with the context it reads.

A stored company website or finding source URL does not cause a fetch. Research runs in the user’s harness under its own settings. Company logo addresses are the explicit guarded-image-fetch exception, including when supplied through MCP. Treat findings and narratives as untrusted data, preserve source uncertainty, and review generated wording: valid citations and matching numbers do not prove semantic support. Clearing live context does not erase historical generation snapshots.
